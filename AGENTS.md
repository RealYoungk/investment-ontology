# Flutter & Serverpod project

This project is a Flutter app (frontend) backed by a Serverpod server (backend). Always build the app's backend with Serverpod.
User decision confirmed 2026-10-01: shared company data remains publicly readable; personal account features require Serverpod email authentication, and mutations require Scope.admin via OntologyAccess. Encourage signup through personal features. See docs/access-control.md. Never bypass account or mutation checks for local use or tests; use authentication overrides in isolated tests.

## Agent skills

Claude Code loads project skills from `.claude/skills/`, Codex and other editors from `.agents/skills/`. Use `serverpod-overview` at least once for Serverpod work, then load the skill matching the task. The dependency-provided `serverpod-*` skills are installed with `user-invocable: false`, so they never appear in the `/` menu; the model loads them itself, and the hand-written `/serverpod <topic>` skill (`.claude/skills/serverpod/`, tracked in git) routes to the right one and reads the official docs (every docs.serverpod.dev page is available as markdown by appending `.md`; index at `https://docs.serverpod.dev/llms.txt`). To install or refresh the dependency-provided skills from the workspace root, run `dart pub global activate skills` if the skills CLI is missing, then `dart pub global run skills get --agent claude --all` (and `--agent generic --all` for `.agents/skills/`; without `--all`, non-interactive runs only list available changes). The managed skill directories are gitignored, so repeat this setup on a fresh checkout. Do not run `serverpod create .` over this existing project to configure agents.

The user starts the server and Flutter app with `serverpod start`. There is no need to check if the server is running: make the changes and call the `serverpod` MCP tools as needed. If the server is not running, an informative error message will be received from the MCP server. Then STOP and ask the user to start it. NEVER start the server yourself. The Flutter app is started along with it, or can be launched from the MCP tool `spawn_flutter_app`.

While running, `serverpod start` watches for file changes to run incremental code generation and hot reload both the server and the Flutter app.

Code generation normally runs automatically. Do not run `serverpod generate --force` after every server edit. After endpoint or FutureCall changes, verify registration with `dart test test/unit/generated_code_test.dart` in the server package. Inspect MCP logs first if generation is incomplete; the CLI fallback conditions below still apply.

ALWAYS use the MCP server instead of the command line. Use the MCP server to:

- `create_migration` and `apply_migrations` for database (after you change data models).
- `create_repair_migration` if the database has drifted out of sync with the migrations.
- `tail_server_logs` to read logs from the server.
- `tail_flutter_logs` to read the raw stdout/stderr of the Flutter app.
- `hot_reload` / `hot_restart` to reload or restart the server and the Flutter app. ALWAYS call `hot_restart` after doing changes in the Flutter app that may not work with normal hot reload (which is automatically applied).
- `spawn_flutter_app` to start a Flutter app declared under `serverpod: flutter_apps:` in the server `pubspec.yaml`.
- `get_flutter_app_dtd` (Dart tooling daemon) for connecting to the app through the `dart` MCP.

NEVER edit generated code. The server's `lib/src/generated/` directory and the whole `investment_ontology_serverpod_client` package are rewritten by the code generator. Change the `.spy.yaml` models, the endpoints, or `lib/server.dart` instead.

Migrations are a narrow exception: the `migration.sql` of a generated migration MAY be edited by hand when the generated SQL would lose data — to add a data transformation, or to reach a destructive change through non-destructive steps. Never touch the other files in the migration directory, and keep the schema the SQL ends up with identical to `definition.sql` — new databases are created from that file and never run `migration.sql`.

Only when the server cannot be started at all, fall back to the CLI in the server package:

- `serverpod generate` to regenerate the client and the generated server code.
- `serverpod create-migration` after changing a model with a `table` (add `--force` for destructive changes). It only writes the migration; `serverpod start` applies pending migrations when it boots the server.

Tests need no Docker. `config/test.yaml` sets `database.dataPath`, so Serverpod starts and manages the test database (an embedded PostgreSQL) itself, and the project's `docker-compose.yaml` is not used for it. Use `bash scripts/test-server.sh` from the repository root on a clean checkout; it supplies a synthetic test-only DB password required by Serverpod configuration. No real credentials or Docker are needed.

Checklist after doing changes, in this order:

- `dart analyze` (CLI)
- `dart format` (CLI)
- `create_migration` and `apply_migrations` (MCP - only if necessary)
- Do `serverpod` MCP `hot_restart` if required (hot reload is done automatically). Will also hot restart Flutter app
- Run tests, if applicable (`dart test` in the server package)
- Check `serverpod` MCP `tail_server_logs` and `tail_flutter_logs` for any issues.

If the user asks you to test the app:

1. Use `get_flutter_app_dtd` (`serverpod` MCP) to get the Flutter app's DTD
2. Pass the DTD to `dtd(command: "connect", uri: ...)` (`dart_mcp` MCP) to connect to the app. If the URI is null, the app has not published its DTD yet; do not pass null to connect. `dtd(command: "listDtdUris")` can discover available instances, and `dtd(command: "listConnectedApps")` confirms the connected app.
3. Use `flutter_driver_command` (`dart_mcp` MCP) to navigate through the app

The app is launched from `investment_ontology_serverpod_flutter/lib/driver.dart`, which starts the Flutter driver extension with text entry emulation turned off so the app stays usable by hand. For automated typing, use `flutter_driver_command(command: "set_text_entry_emulation", enabled: "true")` on the connected app, and restore it to `"false"` after testing.

## About this app: 투자 온톨로지

A tool for building an investment ontology of Korean listed companies and exploring shared data visually (Flutter Web), with authenticated readers and administrators. Design doc: `docs/ontology-design.md`.

Principles: numbers come only from primary sources (DART OpenAPI and public market-data APIs); every fact carries a `Source`. Current user decision (2026-09-22): prioritize rule-based extraction with automatic validation. Manual/AI-written business summaries and manually read prose facts are paused until the user explicitly resumes them. Do not create a routine human-review queue. Existing AI/review implementations and historical records below describe capabilities, not authorization to run them.

Current state (phase 1 — listed-company master, phase 2 — financials and market data, phase 3 — 정기보고서 주요정보 and governance graph):

  - `dart/dart_client.dart` — DART OpenAPI client (`corpCode.xml`, `company.json`), throttled to ~5 calls/s.
  - `ingest/` — `CompanyMasterSync` (run as `CompanyMasterFutureCall`; incremental by DART change date, full refresh every 30 days), `KsicSeeder` (loads both KSIC 10 and 11 from `assets/ksic/`), `KsicRevision` (decides which KSIC revision DART's industry codes follow, from codes unique to one revision; cached, invalidated after each sync).
  - `tool/ksic/` — reproducible extraction of the KSIC assets from the official 국가데이터처 notices. Never hand-edit `assets/ksic/*.json`.
  - `endpoints/` — `company` (overview, divisions, list, detail) and `ingest` (startCompanyMaster, cancel, latest, `schedule` = daily FutureCall entries + last job per kind for the data page's 지금 상태).

Facts are keyed by (document, kind, label, asOf), so one table can carry several years. `disclosure/production_facts.dart` reads the 생산능력·생산실적·가동률 table by rule (no AI, `extractedBy: api`, auto-verified) when 가동률 ≈ 생산실적 ÷ 생산능력, a 가동률-only table when the header names the numerator (실제…) and denominator (…가능) columns, and the vertical shape where 생산능력/생산실적/가동률 are consecutive rows of a 구분 column (당기 = first number after that cell). The unit may sit on the line above the header ("(단위 : 천㎡, %)", within 6 lines, first non-% part; header/label/category parentheses are also checked); when no single unit can be found (per-product units, none printed) the 가동률 is still stored and only 생산능력·생산실적 are dropped — this doubled utilization coverage (51 → 85 companies) on 2026-09-22. It skips sections headed by another listed company's name in brackets and skips 지주회사 (KSIC 64992) documents entirely, since those tables belong to subsidiaries. `disclosure/supplier_rows.dart` + `supplier_relations.dart` do the same for the 원재료 매입처 column, the "주요 매출처는 A, B 등" sentence and the "주요 매출처 | 매출액 | 비중" table (`SupplierRows.customerRows`: only a header cell that is exactly 매출처/주요 매출처, a share or amount header beside it, value rows must contain a number; the 비중 becomes the relation's `weight`, dropped when one cell lists several names; ", Ltd."/", Inc" commas do not split a name; 총계·기타거래처·제조회사·매출비중 and the filer's own English name are not customers) → 공급·매출 relations. Only a column headed 매입처 is used: some filers list counterparties in 비고, where part names creep in. A loose header regex (거래처·고객사) once inserted 1,135 junk relations from 판매경로·결제조건 tables — keep it strict and eyeball every new row after a replay. `disclosure/segment_revenue.dart` reads 부문별 매출 the same way, validated by the 비중 printed in the table (against the 합계 row, or against the sum of rows when the 합계 is after 연결조정); it also accepts the two-line header ("금액 | 비중" under years, only when 매출 is mentioned within 3 lines), the one-cell form "312,776,938 (79.4%)" under a 매출액(비율) header, and 부문별 재무정보 tables where 영업이익·자산 rows share the 비중 column (those rows are skipped and the 매출액 word is dropped from the label); 매출처별 tables are excluded. `disclosure/order_facts.dart` reads the 수주상황 table in three shapes — standard (수주총액·기납품액·수주잔고), construction (기본도급액·완성공사액·계약잔액, same equation) and flow (기초/이월 + 신규/당기 − 기납품액 = 기말 수주잔고; zeros from quantity columns are dropped before summing): in each row it takes the numbers that satisfy the equation (quantity columns satisfy it too, so the largest-총액 triple wins), stores only the 합계 row when there is one ("합계 (2)" for a second table; when a document has any 합계 table the row-level entries of 합계-less tables are dropped, since those are subsidiaries' one-line tables), skips project-detail tables (header with 공사명·현장명·사업명·계약명·수주처명, spaced or not) because their totals are not the company's, carries the item label into continuation rows ("철근 (2)"), and drops tables whose unit is not money (`SegmentRevenue.pickUnit`: "USD 1,000" → USD천, two currencies → none). Backlogs stated only in prose (현대건설 연결 계약잔액, DL이앤씨, LIG·KAI 기말 수주잔액) go in as reviewed `DocumentFact`s via `tool/digest/submit.py` facts files. All three run from `ProductionFacts.store`, which must not return early when the 가동률 table is missing (that bug hid 부문별 매출 for ~100 companies until 2026-09-22). **Columns are picked by header name and then re-found from the right edge of each row** — filings routinely print 당기·전기·전전기 side by side, and taking the last cells stores a three-year-old figure that still passes the self-check (this happened: 삼성물산 상사 20.2조 was stored as 13.2조). Segment-revenue and order tables use a unit within 3 lines above the header and consume it once. Production tables also inspect parentheses and units within 6 lines; section boundaries and stale unit windows are reset and covered by production_unit_boundary_test.dart; arbitrary adjacent tables without section markers remain outside that guarantee.
