# 기업 발견을 위한 산업·사업 분류 v2

2026-10-01 · 설계 검토본. 운영 분류를 변경하지 않았다. 이 문서는 이전 `industry-discovery-design.md`의 검색 진입 및 혼합 분류 설계를 대체한다. 사용자가 제시한 CDMO/ADC 등의 예시는 문제 제기이며 요구 항목 목록으로 취급하지 않는다.

## 1. 설계 결론

‘같은 산업에서 어떤 사업을 하는 기업이 있는지 발견하고, 같은 사업 기준으로 비교할 후보를 고르는 것’이 목적이다. 산업 지수를 복제하거나 인기 테마를 많이 보여주는 것이 목적은 아니다.

**분류 대상은 기업의 사업 활동이다.** 회사는 활동을 여러 개 가질 수 있다. 공식 회사 업종은 별도 보존한다. 사용자는 `관심 산업 → 제공하는 제품·서비스 → 비교에 필요한 차이` 순서로 좁힌다. 중간 단계마다 기업을 볼 수 있고 자유 검색은 없다.

전 산업에 고정된 세부 항목을 강요하지 않는다. 공통으로 고정하는 것은 질문과 데이터 규칙이다.

- 관심 산업: 어느 시장의 기업을 찾는가?
- 제공하는 것: 이 회사에서 고객이 사는 것은 무엇인가?
- 세부 조건: 그 제품·서비스의 기능, 적용 대상, 기술, 사업 방식이 같은가?
- 기업 근거: 왜 이 조건에 해당하고, 어디까지 확인됐는가?

예: 반도체 → 장비 → 검사·계측 → 패키지기판. `검사 장비`와 `검사 대행`은 고객이 사는 것이 달라 별개 활동이다. 같은 회사가 둘 다 하면 각각의 근거로 두 활동을 갖는다.

## 2. 공식 체계를 어떻게 사용할 것인가

| 참고 체계 | 실제로 채택할 원칙 | 채택하지 않는 주장 |
|---|---|---|
| MSCI/S&P GICS | 산업의 정의와 포함·제외 경계, 주사업 판단과 부수 사업 구분 | KSIC를 바꿔 적은 값을 공식 GICS라고 부르지 않는다. |
| FTSE Russell ICB | 매출 출처와 공시 사업 정의를 이용하는 배정 규칙, 근거 부족 시 근거 수준 구별 | GICS와 ICB의 수치 기준을 섞어 자체 분류를 공식이라고 부르지 않는다. |
| SIA 반도체 가치사슬 | 설계·제조·패키징/테스트 단계와 공급 활동을 구별 | 단계가 같다는 이유로 IP, 설계 서비스, 장비를 같은 피어로 묶지 않는다. |
| KSIC/DART 등록업종 | 원래 코드·개정판·명칭을 공식 등록 정보로 유지 | 등록 업종에서 세부 제품이나 공정을 추측하지 않는다. |

원문 근거:

- [GICS 방법론 April 2026](https://www.msci.com/indexes/documents/methodology/1_MSCI_Global_Industry_Classification_Standard_GICS_Methodology_20250220.pdf): 1.1/1.2, 3.1, 7. 주사업과 공식 산업 정의를 참고한다. 회사별 라이선스 데이터는 이번 작업에서 확보하지 않았다.
- [ICB Ground Rules v5.1, August 2026](https://www.lseg.com/content/dam/ftse-russell/en_us/documents/ground-rules/icb-ground-rules.pdf): 4.2.1. 검색 엔진/Exa에는 v5.0 문구가 남아 있었으나 직접 연 원문은 v5.1이다. 원문을 기준으로 삼았다.
- [SIA의 생산 단계와 사업 모델 설명](https://www.semiconductors.org/semiconductor-industry-primer-the-stages-of-production-and-business-models/): 설계, 웨이퍼 제조, 조립·테스트·패키징 및 이를 수행하는 사업 모델을 구분한다. 2015년 기초 설명 자료이며 최신 시장 점유율 근거로 쓰지 않는다.

**화면의 사업 탐색 분류는 알파인더 자체 분류다.** `분류 기준`에서 공식 참고 정의와 자체 확장 부분을 명시한다. MSCI 로고나 ‘MSCI 공식 분류 적용’ 배지는 사용하지 않는다. 회사의 공식 GICS/ICB 배정은 출처·권한·기준일을 갖춘 데이터가 있을 때만 표시한다.

## 3. 현재 구현에서 바꿔야 할 구조

| 현재 | v2 |
|---|---|
| KSIC fallback과 공시 활동이 같은 role 버튼에 혼합 | 사업 활동 결과와 등록 업종 탐색을 별도 결과 집합으로 관리 |
| 공시 규칙이 한 번 맞으면 같은 산업의 등록 분류를 대체 | 회사 등록 분류는 불변. 근거 있는 활동만 추가/갱신 |
| 반도체 제조 장비 / 장비가 중복 | 제품·서비스 사전에 장비 노드 하나. KSIC 명칭은 근거에만 표시 |
| 설계 IP·디자인하우스를 합침 | IP 공급과 설계 수탁을 별도 공급 활동으로 분리 |
| 신약 개발과 기술이전을 같은 제품 키처럼 처리 | 개발 활동과 사업화 방식 분리. 실제 기술이전 계약 여부도 별도 사실 |
| 정규식에서 우연히 잘 잡힌 종류가 곧 화면 분류표 | 먼저 분류 정의를 고정하고 각 노드의 규칙·데이터 충족도를 표시 |
| 374개 그룹 같은 숫자를 성과로 사용 | 노드별 근거 정확도, 누락, 최신성, 실제 비교 과제 성공 여부로 판단 |

등록 정보만 있는 회사는 업종 전체에서 `등록 업종으로 찾기`를 펼치면 볼 수 있다. 사업 세부 필터 결과에 섞거나 ‘기타 사업’으로 몰아넣지 않는다. 화면에 ‘세부 사업을 아직 확인하지 못한 기업도 있어요’와 해당 범위의 정확한 수를 제공한다. 신규 활동을 확보해도 등록 정보는 유지한다.

## 4. 반도체: 고객이 사는 것에 따른 공급 활동

아래는 자체 탐색 노드의 포함·제외 정의다. 회사 배정 완료 목록이 아니다.

| 공급 활동 | 포함 조건 | 제외/경계 | 다음 선택 |
|---|---|---|---|
| 칩 제품 | 자체 칩 제품의 설계·판매 또는 제조·판매가 확인됨 | 설계 수탁만, 칩 유통만 제외. Fabless/IDM은 제조 방식 속성 | 메모리·연산·제어·아날로그·전력·센서 등 칩 기능 |
| 설계 IP | 재사용 가능한 반도체 설계 IP를 외부 제공/라이선스 | 자사 칩 설계에 IP 사용, 고객사 기술 소개 제외 | 인터페이스·프로세서·영상 등 IP 기능 |
| 설계 서비스 | 고객의 칩 설계·구현·검증을 수탁 | 자체 제품 설계만 제외. IP도 팔면 독립 활동 추가 | 설계 구현·검증·양산 지원 등 확인 범위 |
| 웨이퍼 제조 서비스 | 고객 설계에 따른 웨이퍼 제조 수탁 확인 | 자체 칩만 제조, 장비 공급 제외 | 공정 종류·노드(수탁 범위 근거가 있을 때) |
| 패키징·테스트 서비스 | 고객 반도체의 패키징 또는 테스트를 수탁 | 장비 제조사, 일반 산업 시험기관 제외 | 패키징/테스트 → 대상/방식 |
| 장비 | 반도체 공정에 사용되는 장비를 공급 | 해당 장비 사용자, 단순 장비 부품 공급 제외 | 공정·기능 → 적용 대상 → 기술 방식 |
| 소재 | 공정 투입 재료·가스·화학품 등 공급 확인 | 범용 소재의 고객이 반도체라는 사실만으로 세부 공정 부여 금지 | 소재군 → 적용 공정(확인 시) |
| 부품·소모품 | 장비/테스트용 부품 또는 교체 소모품 공급 | 완성 장비, 웨이퍼 원재료와 구별 | 부품 기능 → 적용 장비/공정 |
| 유통·유지보수 | 타사 반도체 제품 유통 또는 유지보수 서비스 | 자체 제조·개발로 승격하지 않음 | 유통/유지보수 → 취급 대상 |

장비의 공정·기능은 노광, 증착, 식각, 세정, 열처리, 평탄화, 검사·계측, 전기적 테스트, 조립·접합, 이송 등으로 정의한다. 서로 다른 기준인 공정/대상/방식을 한 목록에 넣지 않는다. `광학`은 방식, `패키지기판`은 대상, `검사·계측`은 기능이다. 장비를 선택했을 때 `설계` 같은 무관한 필터를 노출하지 않는다.

IDM은 회사 사업 모델을 설명하는 속성이며 `칩 제품`과 동급 노드가 아니다. 지주회사라는 이유로 자회사의 장비 활동을 그대로 부여하지 않는다. 연결 사업을 지원하게 될 때도 연결/별도 범위를 명시하고 운영 자회사를 함께 표시한다.

## 5. 헬스케어: 기술 이름에 앞서 제품과 서비스를 나눈다

기존 제약/의료기기 진입을 ‘헬스케어’ 묶음 아래 놓고 다음 제공물을 바로 선택할 수 있게 한다. 사용자가 반드시 상위 묶음을 한 번 더 클릭하게 만들지는 않는다.

| 제공물 | 정의 | 다음 선택 |
|---|---|---|
| 의약품·치료제 | 자체 후보물질/치료 제품 개발 또는 판매 사업 | 개발·기술사업화 / 제품 판매, 제품 유형, 기술, 적응증, 단계 |
| 의약 원료·중간체 | 제약사 등에 공급하는 원료/중간체 제품 | 합성·바이오 원료 등 제품 종류, 생산 역할 |
| 개발·생산 수탁 | 고객의 의약품 개발·제조를 수행하는 서비스 | 개발·공정 지원 / 제조(CMO·CDMO), 대상 제품 |
| 연구·임상 지원 | 연구 도구·시약·분석·비임상/임상 수탁 등 | 도구·소모품 / 분석·시험 / 임상 운영 |
| 진단 제품·소프트웨어 | 진단 목적의 장비·시약·소프트웨어 제품 | 체외진단 / 영상·분석 / 진단 소프트웨어, 기술·대상 |
| 치료·수술·관리 기기 | 진단 외 의료기기·의료용품 제품 | 치과 / 수술 / 치료 / 관리 등 용도와 제품 |
| 의료·검사 서비스 | 환자 또는 의료기관에 제공하는 진료·검사 서비스 | 진료 / 검사 / 운영 지원 |
| 의약·의료 유통 | 타사 의약품·의료 제품을 유통 | 취급 제품과 유통 방식 |

‘바이오텍’은 사용자 친화적인 산업/기업 설명으로 활용할 수 있지만, 경제적 사업 방식 하나를 정확하게 뜻하지 않으므로 위 모든 항목과 동급의 만능 분류로 사용하지 않는다. 첫 화면은 ‘의약품·치료제’ 아래 ‘신약을 개발하거나 의약품을 판매해요’처럼 설명하고, 세부 선택에서 개발·기술사업화를 드러낸다.

기술은 별도 통제 사전이다. 예를 들어 항체 기반 기술, 접합 기술, 단백질 분해 접근, 세포/유전자 기반 기술 등이 있으며, 조합 가능한 태그와 부모-자식 관계를 갖는다. ADC·이중항체 등은 동일 후보물질에 함께 해당할 수 있으므로 단일 선택 트리로 강제하지 않는다. 목록은 사용자 예시로 확정하지 않고 전문 용어 정의와 제품/파이프라인 근거가 확보된 항목부터 공개한다. 정확한 기술 사전과 동의어 정의는 별도 도메인 검증이 필요한 배포 조건이다.

AI는 업종이 아니라 적용 기술 속성이다. AI 진단 제품과 AI를 이용한 신약 연구는 제공물이 다르므로 별도 경로다. 기술을 ‘사용함’과 외부 고객에게 해당 제품·서비스를 ‘제공함’을 분리한다. 개발 후보의 존재, 임상 단계, 승인, 판매는 서로 다른 상태이며 개발 중 제품을 판매 중으로 표시하지 않는다.

## 6. 전체 업종 확장 범위

다음은 기존 39개 입구를 검토하기 위한 공급 활동 사전의 범위다. 공식 GICS 하위업종표도, 기업 배정 완료표도 아니다. 공통 원칙은 고객이 구매하는 제공물로 1차 구분하고 기술/지역/사업 방식은 속성으로 두는 것이다. 분류마다 별도의 포함/제외 정의와 사례 검증을 거쳐야 공개한다.

| 현재 입구 | 제공물 기준으로 정리할 범위 |
|---|---|
| 반도체 | 칩·IP·설계수탁·제조수탁·후공정수탁·장비·소재·부품·유통/정비 |
| 소프트웨어·IT | 소프트웨어 제품·개발수탁·운영서비스·클라우드 인프라; 보안은 기능 |
| 전자부품·IT기기 | 기판·수동부품·디스플레이·컴퓨터·통신기기·전자제조수탁 |
| 게임 | 게임 콘텐츠·개발수탁·퍼블리싱 서비스; PC/모바일은 플랫폼 속성 |
| 배터리 | 셀/팩·소재·장비·관리시스템·회수/재활용; 양극재/분리막은 소재 하위 |
| 화장품 | 자체 제품·개발/제조수탁·원료·용기·유통 |
| 측정·광학 | 측정기기·분석기기·광학부품·검교정 서비스 |
| 통신 | 이동통신·고정통신·위성통신·통신인프라 서비스 |

동일 활동의 여러 입구는 노드 복제가 아니라 동일 ID를 참조하는 바로가기다. 예: 반도체 생산장비가 ‘기계’와 ‘반도체’에서 발견되어도 기업 수를 합산하지 않는다. 업종별 그룹 수를 동일하게 맞추지 않는다. 한 회사뿐인 명확한 사업도 허용하고, 기업 수를 채우려고 다른 사업을 합치지 않는다.

## 7. 배정 규칙과 상태

각 분류 노드에는 stable ID, 상위 노드, 한 문장 정의, 포함/제외 규칙, 적용 가능한 속성, 공식 참고자료, 자체 확장 여부, 규칙 버전을 둔다. 표시명 변경은 ID를 바꾸지 않는다.

기업 활동은 `주체 → 제공물 → 역할 → 속성`을 같은 제품/사업 근거 안에서 확인한다. 고객 설명, 산업 전망, 자회사 소개, 매입 제품, 미래 계획을 활동으로 승격하지 않는다. 표 머리글과 문서 절 경계를 함께 검사한다. 회사명이나 등록 코드만으로 기술 속성을 추가하지 않는다.

상태는 숫자 confidence 대신 실제 근거로 표시한다.

- 사업 공시 확인: 해당 활동의 제공을 확인. 판매나 매출을 자동 의미하지 않는다.
- 매출 확인: 같은 기간·같은 범위의 해당 활동 매출이 확인됨. 연결/별도와 분모를 함께 보존한다.
- 개발 중: 후보/제품 개발이 확인됐으나 판매 여부는 별도.
- 등록 업종만 확인: 활동 분류 결과와 분리한다.
- 오래된 근거: 최신 갱신이 없어 현행 활동 여부 미확인. 누락과 사업 철수를 구별한다.

‘주력’ 배지는 지금은 도입하지 않는다. 공식 회사 업종과 별개로 ‘매출 비중 가장 큼’을 표시하려면 동일 기간·범위에서 비교 가능한 전체 사업 매출 구성이 있어야 한다. 자의적으로 매출 50/60% 규칙을 혼합하지 않는다. 무매출 신약기업도 개발 활동으로 발견 가능하지만 주력 매출을 만들어내지 않는다.

유효한 최신 문서/정정/기준일을 저장한다. 최신 공시에서 기존 표현이 사라졌다는 사실만으로 철수로 단정하지 않는다. 새 규칙 배포 시 이전 배정과 차이, 추가/제외 사유를 산출한다. 미래시점 정보를 과거 분류에 섞지 않는다.

## 8. 화면 흐름

1. 기업 찾기 → 하는 일로 찾기. 산업 입구를 분야별로 묶어 한 화면에 제공. 검색 없음.
2. 산업 선택 즉시 ‘무엇을 제공하나요?’ 버튼과 결과 표시. 산업별 1차 활동만 같은 줄에 둔다. 버튼 옆 `분류 기준` 한 곳에서 정의/제외/출처를 펼친다.
3. 활동을 고르면 해당 활동에만 유효한 제품·공정·대상 조건을 버튼으로 공개한다. 긴 목록은 의미가 정의된 묶음과 ‘모두 보기’로 확장하며 검색·드롭다운에 숨기지 않는다.
4. 기술부터 찾는 경우 동일 사전의 `기술·공정으로 보기` 전환 제공. 같은 데이터의 다른 보기이며 결과를 ‘칩/IP/장비/서비스’ 등 실제 역할별로 다시 구분한다. 기술만 같으면 피어 확정하지 않는다.
5. 기업 카드: 이름 / 현재 조건에 해당하는 사업 한 줄 / 근거 상태·기간 / 비교 선택. 증거 원문과 공식 등록정보는 펼침 안에 둔다. 분류 기준 설명을 매 카드에서 반복하지 않는다.
6. 결과 기본 10개, 서버 페이지 처리. 다음 10개. 선택 상태·URL·뒤로가기·스크롤 복원. 비교는 최대 4개.
7. 데이터가 없는 노드는 ‘기업이 없음’ 대신 ‘아직 사업 근거를 확보하지 못했어요’. 시장에 기업이 없다는 주장과 구별한다. 알려진 분류를 조용히 숨겨 체계가 없는 것처럼 보이게 하지 않는다.

각 속성 내부 복수 선택은 OR, 서로 다른 속성은 AND다. 모든 사업 조건은 **동일 활동**에서 충족한다. 회사 단위 조건(시장/재무)은 그 다음 AND. 칩 설계와 장비 증착 조건을 억지로 결합하지 않도록 종속 조건을 해제하고 화면에 짧게 알린다. 해제된 조건을 URL에 남기지 않는다.

등록 업종만 있는 회사는 결과 하단 별도 링크로 탐색한다. 공시 확인 회사 수와 등록 회사 수는 중복 제거/부분집합 관계를 설명하고 합계를 단순히 더하지 않는다. 특정 산업에서 공시가 확인된 회사라도 선택한 세부 활동 근거가 없으면 해당 세부 결과에는 넣지 않는다.

## 9. 피어 비교 기준

기본은 ‘비교 후보’다. ‘동종 기업 확정’이나 직접 경쟁을 자동 주장하지 않는다.

| 관계 | 최소 조건 | 보여줄 표현 |
|---|---|---|
| 같은 사업 비교 후보 | 같은 제공물·역할. 산업별 필수 대상/기능 일치 | 함께 비교할 수 있는 사업: ○○ |
| 같은 기술 관련 기업 | 기술만 공통, 역할/제품 다름 | 같은 기술을 다루는 기업 · 사업은 다름 |
| 같은 산업 기업 | 산업/등록만 공통 | 같은 산업에서 더 보기 |

반도체 검사 장비의 최소 비교 키는 제공물=장비 + 기능=검사 + 대상. 광학/X선은 차이로 추가 표시. 진단 제품과 의약품 개발은 AI가 같아도 비교 후보로 자동 합치지 않는다. 약물 기술 비교에서는 후보물질/적응증/개발단계와 권리범위가 중요한 차이이며 미확인 항목은 빈칸 대신 확인 전으로 보여준다. 매출/이익 배수를 기계적으로 동일 적용하지 않는다.

## 10. 데이터·API 구현 설계

운영 DB는 읽기 전용 상태이므로 이 설계에서 스키마 변경을 실행하지 않았다. 구현 시 Serverpod 모델/마이그레이션/MCP 절차를 따른다.

- `TaxonomyNode`: 안정 ID, 축, parent, 산업 scope, label, definition, inclusion/exclusion, allowed facets, references, version.
- `CompanyIndustryAssignment`: scheme(KSIC/GICS/ICB), code/revision, source, asOf, assignmentType(official/source-provided). 자체 사업 추정값을 넣지 않는다.
- `BusinessActivity`: 회사, 제공물 leaf, 공급 역할, businessModel, product/asset identity, status, reportingScope, validFrom/To, extractorVersion. 매출과 주력 여부는 별도 근거 없이 채우지 않는다.
- `ActivityFacet`: activityId, dimension, value, evidenceId. 회사 단위 문자열 태그로 대체하지 않는다.
- `ActivityEvidence`: Source 연결, 원문 구간/표 셀, 문서/접수번호, 보고기간, 주체/역할 근거, 검증 규칙. 회사 공시 진술과 독립 검증된 제품 성능을 구별한다.
- `Coverage`: 산업·노드별 문서 확보, 규칙 적용, 근거 통과, 세부 미확인 수. 제외는 규칙 사유별 집계.

`industry.catalog(version)`는 정의/노드와 현황만, `industry.activities(filters,cursor,limit=10)`는 기업 단위 중복 제거한 페이지와 선택 조건별 개수, `industry.evidence(activityId)`는 원문, `industry.compareBasis(activityIds)`는 공통점/차이를 반환한다. 읽기는 공개, 공유 분류 변경은 기존 admin 권한 유지. 정렬 기준·스냅샷 버전을 cursor에 묶어 페이지 중복/누락 방지.

현재 캐시 미스마다 전체 문서를 읽어 파싱하는 경로는 전환한다. 규칙 추출은 수집/재처리 때 선계산, 요청 시 저장 결과만 읽는다. 캐시는 taxonomyVersion + dataVersion + filter로 분리한다. 분류 사전과 규칙은 코드 리뷰 가능한 파일에서 버전 관리하고 검증된 활동만 저장한다. 생성 코드 수동 편집 금지.

## 11. 실제 저장 근거로 본 경계 사례

아래는 2026-10-01 로컬 조회 응답에 포함된 공시 문장을 사용한 설계 검토다. 원문 전체 재검토나 공식 GICS 배정 확인을 의미하지 않는다. 코드와 원문은 프로토타입에서 펼쳐볼 수 있다.

| 사례 | 저장 근거가 허용하는 표시 | 근거만으로 허용하지 않는 주장 |
|---|---|---|
| 퀄리타스반도체 | 인터페이스 IP 공급, 디자인 서비스 언급 | 모든 IP 기업이 같은 칩/고객 시장이라는 결론 |
| 에이디테크놀로지 | 디자인하우스/설계 서비스 | 자체 IP 라이선스 수익 존재를 자동 추가 |
| 기가비스 | 패키지기판 광학 검사 장비와 수리 장비의 두 활동 | 칩 전기적 테스트 대행, 웨이퍼 검사로 확대 |
| 삼성바이오로직스 | 바이오의약품 CDMO 활동 | 특정 신약 기술 소유, 특정 후보물질 개발 주체 |
| 바이넥스 | 바이오의약품 CDMO 활동 | 전체 회사 매출이 CDMO이거나 삼성바이오로직스와 동일 매출 구성 |
| 디앤디파마텍 | 신약 개발·기술사업화 활동 | 해당 문장만으로 특정 모달리티/임상 단계 부여 |

다사업 기업은 회사 전체가 아니라 선택한 활동이 비교 대상임을 카드/비교 화면에 명시한다. 저장 규칙 근거가 부족하면 그 항목은 미확인으로 남긴다. 이 설계 검토를 수동 사업 요약 데이터로 제출하지 않는다.

## 12. 검증과 전환 완료 조건

1. 정의 검사: 모든 노드에 포함/제외/허용 속성이 있고 서로 다른 축의 동일 단계 혼합이 없는지 확인. 용어 사전의 충돌/중복 자동 검사.
2. 정확도: 업종·규칙·자료 형태별 양성/음성 회귀, 고객/자회사/계획/동음어/표경계 사례 포함. 전체 신규 배정의 근거 일치와 주체 검증을 자동 수행.
3. 누락: 새 규칙이 발견한 기업만 평가하지 않는다. 공식 산업 후보군에서 층화 표본을 만들어 빠진 사업을 확인한다. 정확도와 커버리지를 별도로 보고하고 측정 없는 퍼센트는 쓰지 않는다.
4. 피어: IP vs 설계수탁, 장비 vs 수탁서비스, ADC 개발 vs CDMO, AI 진단 vs AI 연구, 모회사 vs 자회사 사례가 자동 혼합되지 않아야 한다.
5. UX: ‘패키지기판 검사 장비 기업 찾기’, ‘바이오의약품 수탁생산 기업 찾기’, ‘분류 근거 보기’, ‘다른 사업과 차이 보기’를 초행 사용자에게 설명 없이 수행하게 한다. 숫자 목표는 실제 사용 실험 후 조정하며 아직 검증했다고 주장하지 않는다.
6. 전체39입구가 사업 기반/등록 기반/미정의 중 어느 상태인지 ledger로 공개. 두 산업 성공을 전 업종 완료로 보고하지 않는다.
7. v1→v2 dry-run 차이 기록, stale URL 명시적 변환, 결과/정렬/카운트/페이지검증, 접근성·모바일 확인 후 적용. 광범위 role을 더 좁은 제품으로 임의 변환하지 않는다. v1 설계 IP·디자인하우스 링크는 두 활동의 합집합으로 보존하고 선택지를 보여준다.
8. 로컬 검증과 운영 배포를 별도 기록. 현재 DB freeze는 유지한다.

## 13. 검토용 화면

`outputs/industry-discovery/design-v2/index.html`은 설계 흐름을 누를 수 있는 독립 프로토타입이다. 반도체/헬스케어에 대한 정의와 위 6개 회사의 저장 근거 표본만 들어 있다. 기업 수는 표본 수이며 전체 시장 수가 아니다. 실제 앱/DB와 연결하지 않는다. 제품/기술을 클릭했다고 회사에 새 사실을 저장하지 않는다.

### 대안 선택 이유

| 대안 | 발견 | 비교 | 유지보수 | 판단 |
|---|---|---|---|---|
| GICS/ICB만 그대로 사용 | 공식 경계가 명확 | 원하는 제품/공정까지 부족 | 회사별 데이터 권한/배정 필요 | 공식 산업 참조로 사용 |
| 회사당 깊은 단일 트리 | 한 위치 찾기 쉬움 | 복합사업과 조합 기술에서 왜곡 | 예외가 늘어남 | 활동별 탐색으로 대체 |
| 익숙한 기술 태그 나열 | 알려진 단어 진입 쉬움 | 역할과 상태가 섞임 | 동의어/유행어 중복 | 보조 보기로 제한 |
| 제공물 중심 + 분리된 속성 | 산업 안에서 하는 일 파악 | 같은 역할·제품으로 좁힘 | 정의·근거·버전 관리 필요 | 이번 권고 |

프로토타입 검증 상태: 6개 기업/7개 저장 근거, 접수번호 형식, 검색 입력 부재, JavaScript 문법 정적 검사 통과. Chrome의 file URL 차단으로 실제 클릭/반응형 검증은 미완료다. 해당 정책을 우회해 실행하지 않았다.
