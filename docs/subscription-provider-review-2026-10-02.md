## 추가 검토: RevenueCat과 Stripe

앞선 본문 작성 때 RevenueCat은 누락됐고 Stripe는 충분히 검토하지 않았다. 다음은 같은 날 공식 문서를 확인한 보완이다.

- RevenueCat은 Apple/Google 인앱 구독 검증·상태·이용권을 통합하는 서비스이며 결제사/스토어 수수료를 대신 없애주지 않는다. 현재 요금은 월 추적 매출 $2,500까지 무료, 기준 도달 후 추적 매출의 1% 안내다. 결제 처리 비용은 별도다.
- 현재 공식 Flutter SDK는 Web도 지원한다. 웹 결제 엔진은 RevenueCat Billing(Stripe PG), Stripe Billing, Paddle Billing이다. 국내 PG를 그대로 꽂는 표준 웹 결제 경로는 이 목록에서 확인되지 않는다. 국내 PG 웹 이용권과 RevenueCat 앱 이용권의 통합은 Serverpod에 별도 설계해야 한다.
- Stripe의 현재 일반 가맹점 지원 국가 전체 목록에는 한국이 없다. 해외 고객에게 판매하거나 한국 고객 카드 결제를 지원하는 것과 한국 사업자로 Stripe 계정을 개설하는 것은 별개다. 지원 국가의 적법한 사업체가 이미 있다면 다시 검토할 수 있지만 결제 때문에 해외 법인을 새로 만드는 것은 초기 비용 최소화 목적에 맞지 않는다.
- RevenueCat + Paddle은 Stripe 직접 계정 없이 웹/앱 통합을 검토할 수 있는 조합이다. Paddle 판매자·상품 승인은 별도이며, 저가 2,900원 상품에 거래당 $0.50 고정 비용이 부담이므로 현재 우선안을 대체하지 않는다.
- 앱에서 실제 Apple/Google 구독을 판매할 때 RevenueCat 도입은 유력한 선택이다. 안정적인 같은 appUserID를 웹/앱 계정에 연결하고 서버 웹훅/조회로 권한을 반영한다. 모바일 SDK의 상태만으로 서버 권한을 부여하지 않는다. 웹 UI Paywall/일부 메서드 제약은 SDK 문서 기준으로 구현 전 확인한다.

자료: https://www.revenuecat.com/pricing , https://www.revenuecat.com/docs/web/overview , https://www.revenuecat.com/docs/getting-started/installation/flutter , https://stripe.com/global

이 추가 검토도 문서 기반이며 SDK 설치·샌드박스 결제 실행 결과는 아니다.

검토일: 2026-10-02 KST. 제안이며 사용자 확정 결정이나 계약 기록이 아니다.

## 결론

현재 우선안은 **포트원 V2 + 토스페이먼츠 카드 빌링을 가입비·연회비 면제 패키지로 도입**하는 것이다. 월 순거래액 5,000만원 미만 포트원 이용료 무료라는 현재 공개 조건과, 일반 카드 가입 경험, 기존 토스 기반 구현의 재사용성을 함께 고려했다. 개별 빌링 계약에 면제가 적용되는지는 아직 확인되지 않았으므로 계약 완료나 고정비 0원 확정으로 표현하지 않는다.

면제 계약이 불가능하면 **토스페이 직접 계약 자동결제**가 공개 가입비·연회비 무료 조건이 가장 명확한 대안이다. 일반 카드 등록보다 토스페이 사용 흐름을 요구한다. 무료 조건과 실제 구독 서비스 승인 여부는 구분한다.

헥토는 유효한 대안이지만 카드 빌링 직접 견적과 고정비 면제는 공개 자료에서 확인하지 못했다. 계좌 기반 내통장결제의 낮은 수수료를 카드 빌링 요율로 취급하지 않는다. 포트원 V2 공개 목록에서 헥토 국내 카드 빌링 지원을 확인하지 못했으므로 신규 V2 조합으로 확정 추천하지 않는다.

## 전제와 현재 코드

- 국내 소비자 대상 Flutter Web + Serverpod. 현재 서버 금액 상수는 KRW 2,900이고 주문명은 광고 제거 1개월이다. 가격 변경 제안은 하지 않는다.
- `docs/monetization-launch-readiness.md`는 공용 데이터 무료 공개, 광고 제거 월 2,900원과 과거 테스트 증거를 기록한다. 이번 검토에서 운영 플래그·실계약·실결제는 다시 확인하지 않았다.
- `billing_loader.js`는 토스 v2 SDK `requestBillingAuth`를 지연 로드한다. Flutter Web은 `dart:js_interop` 브리지로 연결한다.
- `toss_sandbox_gateway.dart`는 발급·청구·동일 주문 조회·삭제·전액 환불을 구현하고 주문/금액/통화/잔액을 검증한다. POST에 안정적인 멱등 키가 필요하다.
- `billing_renewal_service.dart`의 공급자 타입은 `TossPaymentsGateway`로 고정돼 있다. 여러 공급자가 즉시 교체 가능한 추상 인터페이스는 아니다.
- 기존 서버 원장·동의 state·암호화 저장·갱신·해지·권한 처리의 큰 구조는 유지할 수 있다. 공급자 응답/오류 처리와 카드 등록 콜백은 바꿔야 한다.
- 저장소 문서의 과거 테스트 통과를 이번 검토에서 새로 테스트한 결과로 주장하지 않는다. 이번 범위는 소스 검토와 공식 자료 조사이며 코드 변경·PG 테스트 실행은 없다.

### 2,900원 상품의 수수료 민감도

아래는 계약 견적이 아닌 시나리오이며, 거래 수수료 VAT·상품 세금·환불·보험·정산 비용을 제외한 단순 계산이다.

| 가정 요율 | 1명/월 | 100명/월 | 1,000명/월 |
|---|---:|---:|---:|
| 3.2% | 92.8원 | 9,280원 | 92,800원 |
| 2.9% | 84.1원 | 8,410원 | 84,100원 |
| 1.5% | 43.5원 | 4,350원 | 43,500원 |

3.2→2.9% 차이는 100명에서 월 870원이다. 3.2→1.5%도 100명에서 월 4,930원이다. 초기 고정비 면제와 첫 결제 성공률이 더 중요하다. 계좌 등록이 실제 전환율에 미치는 영향은 측정하지 않았으므로 낮아진다고 단정하지 않는다.

## 기술 비교

### 토스 직접 유지

현재 구현에 대한 변경이 가장 작다. 신규 SDK·공급자 API 전환 없이 계약 설정과 운영 검증으로 진행 가능하다. 그러나 기본 가입비와 연관리비를 허용할 이유는 없다. 계약 면제가 확보될 때만 1순위로 올린다.

### 포트원 V2 + 토스 / KCP

Flutter Web에서는 Browser SDK를 현재 JS 브리지와 같은 방식으로 연결 가능하다. Dart 서버는 V2 JSON REST API를 `http`로 호출할 수 있어 전용 Dart 서버 SDK가 필수는 아니다. 카드 번호를 직접 받는 API 방식 대신 PG 제공 카드 등록창을 사용한다.

변경 범위:
1. 브라우저 SDK, checkout DTO의 store/channel/발급 참조, 콜백 처리.
2. 서버 `PaymentGateway` 인터페이스 추출 후 발급/청구/조회/취소/키 삭제의 포트원 구현.
3. 발급 참조·빌링키를 로그인 계정과 연결해 서버 조회로 검증. 브라우저 반환 키만 신뢰하지 않는다.
4. 공급자별 결제 상태와 잔액을 기존 원장 규칙으로 정규화. 안정적 결제 ID와 멱등 키를 유지한다.
5. 서명 검증 웹훅과 서버 조회로 대사. 알림 중복·순서 역전·수신 실패를 처리한다.

월별 청구는 기존 Serverpod 스케줄러가 담당하게 유지한다. 포트원 예약 청구와 기존 FutureCall을 동시에 켜지 않는다. SDK/API 변경은 필요한데 “제휴 계약만 하고 기존 직결 코드를 그대로 써도 된다”는 조건은 확인하지 못했다.

KCP는 V2 카드 등록창을 명시적으로 지원한다. 직접 카드정보 수집 API는 이번 설계에 불필요하다. 토스와 KCP의 실제 카드 등록 UI를 본인 상점 조건에서 실행 비교한 것은 아니다.

### 헥토 직접

공식 카드 등록창 0원 인증 → 서버 결과통보 → 빌키 청구가 가능하다. Flutter Web JS 호출과 Dart HTTP 연동 자체는 가능하다. 다만 SHA-256 요청/응답 해시, AES-256/ECB/PKCS5Padding + Base64 필드, 날짜·시각·거래번호 기반 전문 형식, notiUrl의 별도 HTTP 수신 경로를 구현해야 한다. 기존 RPC endpoint만 만들면 notiUrl 수신이 자동으로 되는 것은 아니다.

읽은 빌링 문서에서 토스와 같은 범용 멱등 헤더 계약을 확인하지 못했다. 이것이 헥토에 중복방지 기능이 없다는 의미는 아니다. 실제 적용 전 동일 거래번호 재요청, 승인 결과 불명 조회, 취소 결과 불명, 키 삭제·유효기간 정책을 확인하고 회귀 검증해야 한다. 기존 안전한 대사 기능을 단순 성공/실패로 축소하지 않는다.

포트원 V2 목록은 헥토 해외 일반결제만 명시하고 국내 카드 정기결제는 확인되지 않는다. V1에는 헥토 정기결제 안내가 있으나 신규 V2 권장 흐름과 다르다. 부재 목록만으로 불가능이라고 단정하지 않되, 확인되지 않은 조합에 구현을 시작하지 않는다.

### 토스페이 직접

토스페이의 별도 API/빌링키 활성화·조회·해지 경로를 사용해야 하며 토스페이먼츠 키/SDK를 재사용하는 것이 아니다. 무료 기본 조건은 가장 명확하지만 토스페이 인증 흐름이 필요하다. 토스페이 이용 경험을 수용하는 MVP라면 합리적이다.

### 부트페이 / 해외 판매대행

부트페이는 SDK·REST와 구독 API를 제공한다. 기존 원장·권한·갱신 시스템이 있는 현재 상태에서 상품·고객·구독 전체를 외부 커머스 원장으로 다시 옮기는 것은 이득이 작다. 청구 주체는 하나만 선택하고 계정 권한은 Serverpod에서 관리한다.

해외 판매대행은 세금·구독 운영 편의가 있지만 거래당 USD 고정비와 국내 결제 경험, 정산/환불 조건이 저가 국내 상품에 맞지 않을 수 있다. 해외 확장 전에는 우선하지 않는다.

## 앱 확장

PG를 고르면 스토어 결제 정책까지 해결되는 것은 아니다. 동일한 Serverpod 계정의 이용 권한에 `provider`와 결제 출처를 구분해 앱 구독을 추가한다. Android 이용 전용 앱과 iOS 웹 도구 동반 앱의 허용 조건은 서로 다르다. 단순 WebView PG 결제로 인앱 수수료를 없애는 설계는 권하지 않는다. 스토어 배포 직전에 당시 지역별 정책을 다시 확인한다.

## 최종 선택 규칙

1. 매출 0원에서 가입비·연관리비·월 최소 이용료·필수 보험 등 확정 지출이 발생하면 초기 후보에서 제외한다.
2. 현재 토스 직접 계약에 모든 고정비 면제가 가능하면 기존 구현을 유지하는 것이 기술적으로 가장 유리하다.
3. 그 조건이 없으면 포트원 V2 + 토스 면제 패키지를 우선한다. 면제가 KCP에만 적용되면 KCP로 진행한다.
4. 포트원에서도 0원 고정비 계약이 안 되면 토스페이 직접 자동결제를 선택한다.
5. 헥토는 위보다 낮은 총비용의 실제 카드 빌링 조건이 확인될 때 대안으로 올린다. 현재 “최저가” 증거는 없다.

공개 자료 기반의 우선안은 제시할 수 있으나 비공개 견적·업종 심사 결과를 만들어낼 수는 없다. 이번 조사에서는 업체에 연락하거나 개인정보를 전달하지 않았다. 서비스는 공시 데이터 도구/광고 제거 상품으로 실제 기능을 설명하고 투자자문 상품으로 임의 분류하지 않는다.

## 변경 후 필요한 검증

실제 적용 시: 카드 등록 취소/복귀·발급 실패, 첫 청구, 중복 클릭/동시 청구, 타임아웃 후 동일 결제 조회, 카드 변경 0원, 월말 갱신, 해지 후 청구 차단, 재가입, 전액 환불, 웹훅 중복/순서 역전, 계정 전환·탈퇴, 키 삭제 실패를 검증한다. 브라우저 모의 테스트와 실제 PG 테스트/실판매는 구분한다. 이번 검토에서는 실행하지 않았다.
