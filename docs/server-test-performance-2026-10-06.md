# 원문 캐시 및 가짜 HTTP 검증의 불필요한 대기 제거 — 2026-10-06

## 결론과 범위

대표 사례로 테스트를 축소하기 전에 더 직접적인 원인을 발견했다. 로컬 파일만 읽는 캐시 검증이 HTTP 조회기를 재사용하면서 요청당 1초를 예약하고 있었다. 캐시의 `_PinnedRawClient`는 네트워크가 없는 구현이지만 조회기에는 이 구분이 없었다. 수집의 `callInterval: Duration.zero`는 조회기 내부 속도 제한을 없애지 않는다.

`PublicFinancialHtmlFetcher.pinnedDocuments`는 닫힌 URL→바이트 맵과 최대 요청 수만 받는다. 외부 HTTP 클라이언트를 받을 수 없고, 등록되지 않은 URL·GET 이외의 요청·요청 한도 초과는 실패한다. 이 내부 transport만 속도 제한을 적용하지 않는다. 일반 생성자의 실제 HTTP/MockClient 경로는 기존 요청 간격 및 여러 조회기 사이의 예약을 유지한다.

`VerifiedAnnualSourceCache`는 기존 manifest/원문 SHA와 회사·접수번호·기간·기준 검증을 마친 후 전용 조회기를 사용한다. 기존 private byte transport를 이동한 변경이며, 파서·금액·출처·권한·API 예산·DB 저장 로직은 바꾸지 않는다.

## 검증 범위 보존

- 원문 registry 317개 전체를 유지한다. 원문별 성공, 9가지 범위 거절, 개별 파일 변조, 기존 DB 수집·재실행 검사 모두 유지.
- 기존 테스트 파일·assertion·회사별 예외를 삭제하거나 대표 사례로 대체하지 않았다. 성공 결과를 저장해 원문 검사 자체를 건너뛰는 캐시도 추가하지 않았다.
- 새 transport 회귀 테스트: 실제 레드우즈 연결 원문의 숫자·출처, cadence timer 부재, 다른 호스트/접수번호/미등록 URL/POST 거절, 요청 수 한도, URL 맵 변경의 영향 방지, 일반 조회기의 요청 간격을 여러 인스턴스 사이에서도 확인.
- package별 보존 목록: `output/server-test-performance/preserved-coverage.json`.

## 실행 환경과 현재 결과

기준 커밋은 `6b99f52b9e25239bec95dcc85bec7635e479f8d2`. 동일 커밋에서 두 격리 폴더를 만들고 after에 변경한 서버 두 파일과 새 테스트 한 파일만 복사했다. 의존성은 lockfile을 유지한다. 운영 서버를 별도로 시작하지 않고 격리된 테스트용 PostgreSQL을 사용하는 공식 테스트 스크립트를 실행한다.

원래 작업 폴더에는 다른 채팅의 미커밋 변경과 Serverpod 4.0.0과 맞지 않는 generated test tools가 있다. 해당 생성 파일을 수정/재생성하거나 다른 작업 변경을 포함하지 않았다. 검증 결과를 원래 dirty 작업 폴더 전체의 통과로 해석하지 않는다.

- 변경한 세 파일 정적 분석 및 격리 snapshot 전체 `dart analyze --fatal-infos`: 통과.
- 새 transport 회귀 테스트: 4개 통과, runner 표시 약 9초(일반 조회기의 실제 간격 확인 포함).
- 변경 후 registry 단위+통합 동시 실행: 기존 4,943개 통과, 프로세스 wall time 134.65초. 준비 비용 포함.
- 변경 전 동일 registry 실행: 기존 4,943개 통과, 849.31초(14분 9초). 변경 후 134.65초(2분 15초)로 84.1% 단축. 두 파일을 같은 명령·기본 동시 실행 설정으로 실행한 프로세스 wall time의 단일 비교다.
- 변경 후 전체 서버 검사: 471개 파일, 19개 묶음, 10,205개 통과, 기본 skip 2개, 1470.91초(24분 31초), 종료코드 0. skip은 외부 fixture 경로를 요구하는 current_product_rows의 실원문 검사와 별도 브라우저 실행용 billing fixture다. skip 조건을 변경하지 않았다.
- 전체 gate 안에서 registry 단위 테스트가 포함된 4번 묶음은 1분 35초, registry 통합 테스트가 포함된 18번 묶음은 1분 56초였다. 이전 배포 로그의 각 12분 30초/14분 19초와 비교할 수 있으나 커밋·동시 실행 조건이 완전히 같은 비교는 위 두 파일 실측만 해당한다.
- 기존 470개 테스트 파일은 before/after 사이에서 바이트 단위로 동일하다. 추가한 회귀 테스트 1개 파일 이외에 변경한 테스트가 없다. `test-preservation.json`과 `summary.json`에 결과를 보존했다.
- 최종 Dart 포맷 검사·diff 공백 검사 통과. Serverpod MCP 최근 서버 로그 200개에서 실패/오류 항목은 없었다. DB/Flutter 변경은 없다.

실행 로그·시간·종료코드·기준 SHA·변경 파일 SHA256·구현 patch는 `output/server-test-performance/`에 남긴다. 과거 서버 전체 검사 51분 19초는 다른 커밋의 기록이므로 현재 24분 31초와의 차이를 동일 조건의 단축률로 주장하지 않는다. 반복 측정·단독 실행 조건에 따라 실제 배포 시간은 달라질 수 있다.

대표 사례로 테스트를 줄이는 변경은 적용하지 않았다. 불필요한 로컬 대기를 제거하는 것만으로 큰 효과가 확인되어 전체 원문/DB 회귀를 유지하는 쪽을 선택했다. 운영 배포 완료를 뜻하지 않는다.


## 추가 개선: 가짜 HTTP의 요청 간격을 가상 시간으로 실행

`FinancialHtmlRequestTiming`에 요청 시작 예약과 대기만 분리했다. 일반 조회기는 하나의 실제 시계를 공유하고 기존 1초 간격을 적용한다. pinned 문서는 간격 시계를 사용하지 않는다. HTTP timeout, 파싱, URL/회사/기간/금액 검증은 이 시계와 독립적이다.

테스트 전용 `fastFinancialHtmlFetcher`는 `MockClient`만 받는다. 67개 기존 fixture 테스트 파일에서 이 helper를 사용하며, 같은 원문 응답과 assertion을 실행한다. 테스트 시계는 1초 예약을 가상 시간으로 진행하므로 실제 sleep도 1ms sleep도 사용하지 않는다. 일반 생성자의 실제 요청 간격 smoke test는 변경하지 않았다. 운영 코드에는 testing 생성자의 사용 지점을 추가하지 않았다.

새 요청 간격 테스트 3개는 첫 요청 무대기, 조회기 호출 경계를 넘는 annual 예약, 충분한 idle 후 추가 대기 없음, attachment 후속 요청의 1초 대기를 확인한다. 기존 471개 테스트 파일의 Dart 토큰을 비교해 helper 호출·import·포맷 이외의 변경이 없음을 확인했다 (`output/server-test-virtual-clock/test-preservation.json`).

지난 전체 측정에 사용한 격리 snapshot을 기준으로 이번 변경만 덧씌웠다. 분석 전체 통과, 집중 검사 21개 통과. 실제 작업 폴더의 다른 수정과 generated test-tools 호환성 문제는 측정에 포함하지 않았다. 전체 측정은 472개 파일·19개 묶음이며 결과는 아래에 기록한다.

- 배포 전체가 아닌 서버 검사만 실측: **698.30초(11분 38초)**, 종료코드 0.
- 이전 **1470.91초(24분 31초)**에서 **772.61초(12분 53초), 52.5% 단축**. 같은 이전 snapshot과 테스트 스크립트를 기준으로 한 단일 실행 비교이며, 머신 부하 등에 따라 달라질 수 있다.
- **472개 파일, 19개 묶음, 10,208개 테스트 통과, 기존 skip 2개**. 기존 10,205개를 유지하고 간격 테스트 3개를 추가했다.
- 실행 로그·보존 비교·변경 파일 SHA·patch는 `output/server-test-virtual-clock/`.
