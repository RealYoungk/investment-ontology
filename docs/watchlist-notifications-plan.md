# 관심종목과 업데이트 알림

작성: 2026-10-01. 사용자 요청에 따라 아래 MVP를 구현했다. 기존 이용권의 결제 확인 기간에 20개, 무료 계정에 3개를 적용한다. 새 가격·결제 상품은 만들지 않았다.

## 구현한 MVP

- 기업 상세 관심등록 버튼과 `/watchlist` 개인 화면. 기업 검색, 등록/해제, 기업별 푸시 음소거, 읽음 처리, 로그인 후 저장 의도 복원.
- 계정별 데이터 접근, 중복 등록 방지, 동시 등록 한도 검증. 결제 종료 시 목록은 보존하고 첫 3개만 활성화하며 다른 기업을 우선 활성화할 수 있다.
- 전체 공시 목록을 10분마다 공유 수집하고 접수번호로 중복 제거한다. 하루 단위 페이지 커서를 보관해 장애 후 이어받는다. 첫 완전 수집은 기준점만 설정하며 과거 공시를 발송하지 않는다. 정정 공시는 새 접수번호의 별도 이벤트다.
- 개인 공시 알림함과 Web Push 대기열. 1분마다 발송 작업, 최대 5회 재시도, 만료 구독 제거, 사용자당 최대 5기기. 수락 상태는 실제 표시를 보장하지 않는다.
- PWA 서비스 워커, 명시적 권한 요청, 계정 전환/로그아웃 구독 정리. 네이티브 모바일 푸시는 아직 연결하지 않았다.
- 뉴스 조회에 회사명 경계와 기업 식별 근거를 검사한다. 아크릴 같은 동명 일반명사는 CEO·종목코드·기업 제품/상장 문맥 등의 근거가 없는 기사를 제외한다. 정확도 수치를 측정하지 않았으며 완전한 분류를 보장하지 않는다. 뉴스 푸시는 활성화하지 않았다.

## 운영 설정과 검증 범위

`shared.webPushPrivateKey` 또는 `WEB_PUSH_PRIVATE_KEY`에 P-256 개인키 32바이트의 base64url 값을 서버에 설정한다. 키는 버전 관리에 넣지 않는다. 공개키는 서버가 파생해 로그인한 클라이언트에 전달한다. DART 키와 `futureCallExecutionEnabled: true`, 적용된 마이그레이션이 있어야 실제 자동 수집이 동작한다. 개발 설정은 자동 수집이 꺼져 있으며 화면에 그 상태를 표시한다. 키가 없으면 푸시 버튼을 비활성화한다.

검증: 격리 DB의 인증·소유자 분리·등록 한도·동시 요청·결제 기간/종료·첫 수집 기준점·중복 알림·읽음 처리 통합 테스트, RFC 8291 암호화 벡터와 VAPID 서명 검증, 뉴스 오탐 회귀, 계정 전환/저장 응답 순서, 390px 위젯 화면, 생성 등록·분석·디자인 경계 테스트. 분리 개발 DB의 합성 계정으로 실제 로그인→기업 검색→관심등록→해제도 확인했다. 브라우저 구독 권한 흐름은 `node investment_ontology_serverpod_flutter/test/web_push_bridge_test.cjs`로 검증한다. 실제 DART 수집과 OS 푸시 표시는 운영 키/브라우저 권한을 연결한 후 별도로 확인해야 한다.

다음 절은 확장 기획이다. 공시 유형별 필터·일일 묶음·방해금지 시간은 이번 MVP에 포함하지 않았다.

## 목적과 경험

공개 기업 탐색 → 관심등록 → 로그인/가입 → 개인 관심종목 화면 → 새로운 공시 확인 → 선택적으로 기기 알림 허용. 공개 조회 정책을 유지한다. 관심종목은 개인 저장이며 공개 테마·비교기업과 구분한다.

- 기업 헤더에 관심등록 버튼과 개인 화면의 기업 검색. 로그인 후 원래 기업과 저장 의도를 복원한다.
- 관심종목 화면: 등록 기업, 미확인 업데이트 수, 최신 공시, 데이터 마지막 확인 시각. 등록과 외부 알림 허용을 분리한다.
- 처음 등록한 뒤 알림의 효용을 설명하고 사용자가 알림 켜기를 누를 때 브라우저 권한을 요청한다. 거부해도 관심등록·앱 내부 알림함을 사용한다.
- 공시 종류 선택, 기업별 음소거, 즉시/일일 묶음, 방해금지 시간. 정정공시는 별도 표시하고 원문으로 연결한다.
- 새 등록의 첫 수집까지는 기준점만 잡고 그 이후 새 공시를 알림함에 기록한다. 수집 장애는 업데이트 없음과 구분한다.

## 요금제 가설

무료 관심종목 3개, 유료 20개로 시작할 수 있다. 무료에도 공시 알림의 핵심 경험을 제공하고 유료에는 등록 확장·세부 필터·묶음 설정을 제안한다. 가격은 지불 의사와 실제 이용 원가를 확인한 뒤 결정한다. 3개 한도에 막힌 비율, 관심등록 유지율, 알림 클릭률, 권한 허용률, 해제율, 유료 전환율을 측정한다.

관심종목 저장과 모니터링을 같은 한도로 시작하면 간단하다. 한도가 재방문을 막는다면 저장은 넓게 허용하고 알림 활성 기업만 제한하는 대안을 검증한다. 유료 종료 시 기존 목록은 보존하고 사용자가 무료 활성 3개를 선택하게 한다. 초과 신규 등록과 초과 알림은 서버에서 제한한다.

## 알림 구조

공시/뉴스 원천 → 공통 업데이트 수집 → 기업별 이벤트 저장 → 관심종목·설정과 매칭 → 개인 알림함 + 발송 대기열 → Web Push / 추후 모바일 Push → 기업 상세나 원문.

동일 기업을 여러 회원이 등록해도 외부 원천 조회는 공유한다. 발송 작업은 수신 회원과 기기 수에 따라 증가한다. 관심종목 수가 그대로 외부 API 호출 수가 되지 않도록 설계한다.

전통적 Web Push는 HTTPS 웹에서 사용자가 허용하면 브라우저가 기기별 구독 주소와 암호화 정보를 만든다. Serverpod가 계정과 연결해 보관하고 이벤트 발생 시 브라우저의 푸시 서비스에 전달한다. 서비스 워커는 수신 시 기동해 OS 알림을 표시하고 클릭 시 앱 경로를 연다. 탭을 열어 둘 필요는 없지만 기기 연결·OS 설정·브라우저 상태에 따라 지연/미전달이 가능하다. 발송 서비스의 수락과 실제 표시·열람은 다르다. 알림함을 기준 기록으로 둔다.

iOS/iPadOS는 16.4 이상 홈 화면에 추가한 웹 앱의 Web Push를 지원한다. 첫 버전은 PWA/Web Push로 검증하고 네이티브 앱 출시 때 같은 서버 알림함과 발송 대기열에 모바일 기기 토큰을 추가한다.

## Serverpod 구현 방향

Serverpod overview 스킬과 현재 인증 정책을 기준으로 한 설계 제안이다.

- WatchlistEntry: 인증 사용자 ID, corpCode, 생성 시각. 사용자×기업 유일 제약. 본인 데이터만 읽고 변경한다. 개인 변경에 관리자 권한을 요구하지 않으며 공유 데이터 변경 권한과 분리한다.
- NotificationPreference: 기업/계정별 유형, 주기, 음소거, KST 방해금지 시간.
- CompanyUpdateEvent: 원천 ID, 기업, 제목, 원문 URL, 원천 게시 시각, 서버 발견 시각. 공시 접수번호로 중복 방지, 정정 접수번호는 별도 이벤트. 기사 URL 정규화와 동일 기사 묶음 처리.
- UserNotification: 사용자×이벤트 유일 제약, 읽음 상태. 재수집/재시도에도 중복 생성 방지.
- PushSubscription: 사용자와 기기별 구독, 활성 상태. 계정 전환·로그아웃 시 구독 연결 해제 정책, 탈퇴 시 삭제. 구독 주소와 키는 공개 데이터나 로그로 노출하지 않는다.
- NotificationDelivery: 알림×구독별 발송 상태, 재시도 시각. 제한된 동시 발송과 일시 실패 재시도, 만료 구독 해제. 발송 수락을 전달 완료로 표기하지 않는다.
- PlanEntitlement: 서버에서 유효 요금제와 한도 검사. 동시 추가는 트랜잭션/잠금으로 한도 초과 방지. 유료 권한은 검증된 결제 이벤트로만 변경한다.
- FutureCall 기반 공통 수집·발송. 기존 IngestHooks 경로로 등록하고 요청 처리 중 외부 수집/AI를 실행하는 방식은 피한다.

## 현재 코드와 차이

company_news_endpoint.dart의 recent는 기업별 최근 뉴스/공시를 조회한다. 뉴스 요청은 동시 요청을 합치지만 완료 결과를 장기 캐시하지 않는다. 공시는 90일 목록의 한 페이지를 조회하고 표시 결과를 제한한다. 이를 알림 수집 장부로 그대로 쓰면 누락될 수 있다. 별도 수집은 페이지네이션, 수집 커서, 구간 겹침 재조회, 장애 후 복구, 중복 제거를 갖춰야 한다.

기존 재무 수집은 정기공시 중심이므로 계약·증자·배당 등 전체 공시 알림을 대신하지 않는다. 기존 DART 호출 예산과 공유하고 알림 수집 몫을 확보한다. 전체 상장사 목록 조회와 등록 기업 합집합 조회 중 호출량이 적은 방식을 원천 API 조건에 맞춰 선택한다.

뉴스는 동명이인 기업, 자회사 언급, 재전송 기사 때문에 공시보다 오탐 관리가 어렵다. 초기에는 기존 뉴스 조회를 유지하고 푸시는 보류한다. 기사 제공 API의 이용·보관 조건을 확인하고 원문 링크 중심으로 처리하며 유료 AI 요약은 별도 원가·품질 검증 전 도입하지 않는다.

## 순서와 검증

1. 로그인 기반 관심종목 3개와 개인 목록, 한도·권한 테스트.
2. 공시 이벤트 수집과 앱 내부 알림함. 중복·정정·장애 복구·미수집 상태 검증.
3. Web Push/PWA. 데스크톱·Android·iPhone 홈 화면에서 권한 허용/거부, 탭 닫기, 클릭 이동, 계정 전환, 구독 만료 검증.
4. 유료 20개와 결제 연동. 실측 원가와 사용자의 반복 이용을 확인한 뒤 출시.
5. 뉴스 묶음과 선택 알림. 기업 매칭 정확도와 중복 비율부터 측정.

공시 수집 주기는 초기 제안으로 주간 5~10분이며 DART 예산·실측 지연에 따라 조정한다. 실시간 보장은 하지 않는다. 원가 지표: 고유 모니터링 기업 수, API 호출 수, 이벤트 수, 발송 기기 수, 실패/재시도율, DB 저장량. 공시 발생→발견→발송 수락 지연을 각각 측정한다.
