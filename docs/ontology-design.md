# 투자 온톨로지 설계 (v0.1)

개인 투자자(1인)가 국내 상장사를 중심으로 기업·산업·지배구조·공급망·테마 관계를 쌓고, Flutter Web에서 탐색·시각화하는 도구.

## 1. 원칙

1. **숫자는 원천에서만.** 재무·시세·지분율 같은 수치는 DART OpenAPI / KRX(공공데이터포털) 응답을 그대로 저장한다. AI가 숫자를 만들거나 고치지 않는다.
2. **모든 사실에는 출처.** 엔티티를 제외한 모든 사실(관계·수치)은 `Source`(공시 접수번호, API 호출, URL)를 반드시 가진다. 출처 없는 사실은 저장 불가.
3. **AI는 텍스트 → 관계 추출에만.** 사업보고서 본문에서 공급망·제품·경쟁 관계를 뽑되, 원문 인용(evidence)을 붙이고 `draft` 상태로 넣는다. 사람이 검수해야 `verified`.
4. **시점을 가진다.** 관계와 수치는 `asOf`(기준일) 또는 회계기간을 가진다. 덮어쓰지 않고 이력으로 쌓는다.
5. **스키마가 형식을 정한다.** 원천 데이터를 스키마 형식(날짜는 DateTime, 월은 1~12 정수 등)으로 정규화해서 넣는다. 형식에 맞지 않는 값은 추측하지 않고 비워 둔다.
6. **식별자는 공식 코드.** 기업 = DART `corp_code`(8자리), 종목 = 단축코드(6자리)·ISIN, 산업 = KSIC(한국표준산업분류).

## 2. 클래스 (노드)

| 클래스 | 식별자 | 주요 속성 | 원천 |
|---|---|---|---|
| **Company** 기업 | `corp_code` | 회사명, 영문명, 법인등록번호, 사업자번호, 대표자, 설립일, 결산월, 시장구분(KOSPI/KOSDAQ/KONEX), 본사주소, 홈페이지 | DART `corpCode.xml`, `company.json` |
| **Security** 종목 | 단축코드, ISIN | 종목명, 주식종류(보통/우선), 상장일, 상장주식수 | DART, KRX 상장종목정보 (2단계. 1단계는 Company.stockCode에 대표 종목만) |
| **Industry** 산업 | 개정 차수 + KSIC 코드 | 분류명, 레벨(대·중·소·세·세세), 상위 코드 | 통계청(현 국가데이터처) 고시 자료 — 제10차·제11차를 모두 저장 (`assets/ksic/`, 추출 스크립트 `tool/ksic/`) |
| **Person** 인물 | 내부 ID (이름+생년월 조합으로 동일인 추정) | 이름, 생년월 | DART 임원·최대주주 현황 |
| **Segment** 사업부문 | 기업+부문명 | 부문명 | 사업보고서 (AI 추출) |
| **Product** 제품·서비스 | 내부 ID | 이름, 설명 | 사업보고서 (AI 추출) |
| **Theme** 테마 | 내부 ID | 이름, 설명 | 사용자 직접 정의 |
| **Source** 출처 | 내부 ID | 종류(dart_report / dart_api / krx_api / manual), 공시 접수번호(`rcept_no`), 보고서명, 제출일, URL, 수집 시각 | — |

## 3. 관계 (엣지)

모든 관계는 공통 속성을 가진다: `source`, `asOf`(또는 기간 `validFrom~validTo`), `extractedBy`(api / ai / manual), `status`(draft / verified / rejected), AI 추출 시 `evidence`(원문 인용)와 `confidence`.

| 관계 | 주어 → 목적어 | 추가 속성 | 원천 | 신뢰 수준 |
|---|---|---|---|---|
| `ISSUES` | Company → Security | — | DART/KRX | 구조화 API |
| `CLASSIFIED_AS` | Company → Industry | — | DART `company.json`의 `induty_code` | 구조화 API |
| `PARENT_OF` | Industry → Industry | — | KSIC | 공식 분류 |
| `LARGEST_SHAREHOLDER_OF` | Person·Company → Company | 지분율, 보유주식수, 관계(본인/특수관계인) | DART `hyslrSttus.json` | 구조화 API |
| `EXECUTIVE_OF` | Person → Company | 직위, 등기여부, 상근여부, 담당업무 | DART `exctvSttus.json` | 구조화 API |
| `INVESTS_IN` | Company → Company | 지분율, 장부가액, 출자목적 | DART `otrCprInvstmntSttus.json` | 구조화 API |
| `HAS_SEGMENT` | Company → Segment | 매출액, 매출비중 | 사업보고서 부문정보 | 원문 수치 + AI 매핑 |
| `PRODUCES` | Company·Segment → Product | 매출비중 | 사업보고서 "주요 제품" | AI 추출 + 검수 |
| `SUPPLIES_TO` | Company → Company | 품목 | 사업보고서 "주요 매출처/원재료 매입처" | AI 추출 + 검수 |
| `COMPETES_WITH` | Company ↔ Company | 경쟁 분야 | 사업보고서 "경쟁 현황" | AI 추출 + 검수 |
| `EXPOSED_TO` | Company·Product → Theme | 노출도 메모 | 사용자 | 수동 |

타법인출자에서 상대 회사가 비상장이면 `corp_code`가 없을 수 있다 → 이름만 가진 **미확인 Company**로 만들고 나중에 병합한다.

## 4. 수치 데이터 (시계열)

그래프 엣지가 아니라 별도 테이블로 저장한다(건수가 많고 집계 쿼리가 필요하므로).

**FinancialFact** — DART `fnlttSinglAcntAll.json` (단일회사 전체 재무제표)
- 기업, 사업연도, 보고서코드(`11011` 사업 / `11012` 반기 / `11013` 1Q / `11014` 3Q), 연결/별도(`CFS`/`OFS`), 재무제표 구분(BS/IS/CIS/CF/SCE — 자본변동표 포함 5종 모두)
- 계정 ID(XBRL, 예: `ifrs-full_Revenue`, 표준계정을 쓰지 않은 계정은 비움), 계정명, 세부(자본변동표의 자본 구성요소), 통화
- 응답 한 행의 **금액 열을 모두** 저장: 당기, 당기 누적, 전기, 전기 누적, 전기 동분기, 전전기와 각 기간명. 모두 **원 단위 정수(BigInt)**, 정수가 아니면 비우고 보고서에 개수를 남김
- `source` = 응답의 `rcept_no`(DART 공시). 사실은 공시 1건 × 연결/별도 1벌인 `FinancialReport`에 묶인다
- 정정공시가 나오면 새 보고서·행을 추가하고, 이전 보고서와 같은 칸(재무제표·계정 ID·계정명·세부)의 이전 행은 `supersededBy`로 새 행을 가리킨다 (삭제하지 않음)

**MarketSnapshot** — 공공데이터포털 금융위원회_주식시세정보(`getStockPriceInfo`)
- 종목(`Security`, ISIN), 기준일, 종가, 전일 대비, 시가·고가·저가, 거래량, 거래대금, 상장주식수, 시가총액 (원 단위 정수)
- `source` = 기준일 × API 호출 기록 (서비스키는 남기지 않음)
- 종목의 발행 기업은 금융위원회_KRX상장종목정보(`getItemInfo`)의 법인등록번호(`crno`)를 `Company.jurirNo`와 맞춰 잇는다. 기업 시가총액 = 연결된 종목(보통주·우선주 등) 시가총액 합

화면에 보여주는 파생 지표(PER, 영업이익률 등)는 저장하지 않고 위 원천 값으로 계산한다. 계산식도 화면에 표시한다.

## 5. 저장 방식

PostgreSQL + Serverpod ORM. 1인·상장사 약 2,700개 규모라 별도 그래프 DB는 필요 없다.

- 노드: 클래스별 테이블 (`company`, `security`, `industry`, `person`, `segment`, `product`, `theme`, `source`)
- 엣지: 공통 `relation` 테이블 (주어 타입·ID, 술어, 목적어 타입·ID, 속성 JSON, source, 기간, status) — 새 관계 종류를 스키마 변경 없이 추가
- 수치: `financial_report`(공시 × 연결/별도), `financial_fact`, `security`, `market_snapshot`
- 변경 이력: `company_change` (필드, 이전 값, 새 값, 출처, 시각) — 다시 수집했을 때 바뀐 필드만 기록. 바뀐 게 없으면 출처도 새로 만들지 않는다
- 수집 작업: `ingest_job` (무엇을, 언제, 성공/실패, 호출 수) — DART 일일 호출 한도(키당 약 20,000건) 관리
- 호출 장부: `api_call_usage` (제공자·KST 날짜별 호출 수) — 여러 수집이 같은 일일 한도를 나눠 쓰므로 작업별 호출 수와 따로 날짜로 합산
- 수집 장부: `dart_filing` (공시 목록에서 찾은 정기보고서와 연결·별도별 수집 상태), `dart_filing_scan` (전체 공시 목록을 어디까지 훑었는지), `market_snapshot_day` (시세를 받은 기준일, 휴장일 포함)
- 수집 장부: `dart_corp_status` (고유번호별 마지막 상장 구분·변경일) — 온톨로지 엔티티가 아니라, 저장하지 않는 상장폐지 기업을 매번 다시 조회하지 않기 위한 기록

## 6. 단계별 계획

| 단계 | 내용 | 화면 |
|---|---|---|
| **1. 상장사 마스터** | `corpCode.xml`로 상장사 목록 → `company.json`으로 기업개황 → KSIC 분류표 적재 | 전체 상장사 테이블(검색, 시장·업종 필터), 기업 상세 페이지 |
| **2. 재무·시세** | 최근 5개년 사업보고서 + 분기 재무 수집, 시세 스냅샷 | 기업 상세에 재무 추이 차트, 업종별 시총 트리맵 |
| **3. 지배구조 그래프** | 최대주주·임원·타법인출자 수집 | 기업 중심 네트워크 그래프 (출자·지배 관계) |
| **4. AI 관계 추출** | 사업보고서 "II. 사업의 내용" → 제품·공급망·경쟁 추출, 인용문 첨부 | 검수 큐 (원문 옆에서 승인/거절), 공급망 그래프 |
| **5. 테마** | 사용자 테마 생성·연결 | 테마별 기업 지도 |

## 7. 준비물

- **DART OpenAPI 인증키** — https://opendart.fss.or.kr (무료)
- **공공데이터포털 서비스키** — 금융위원회_주식시세정보, 금융위원회_KRX상장종목정보 활용 신청 (2단계부터)
- 키는 `config/passwords.yaml`의 `shared:` 아래(`dartApiKey`, `dataGoKrServiceKey`, git 제외됨) 또는 환경변수(`DART_API_KEY`, `DATA_GO_KR_SERVICE_KEY`). 공공데이터포털은 Decoding 키를 넣는다

## 8. 결정 사항

- **증분 수집 + 월 1회 전체 갱신**: 평소에는 DART 변경일이 바뀐 기업만 받는다. 변경일에 반영되지 않는 개황 변경을 놓치지 않도록, 마지막 전체 갱신 후 30일이 지나면 다음 수집을 자동으로 전체 갱신으로 돌린다.
- **KSIC 차수는 데이터로 판정**: DART는 업종코드의 KSIC 차수를 밝히지 않는다. 10차·11차를 모두 저장하고, 한 차수에만 있는 코드(10차의 274, 11차의 109·603·846 등)가 실제로 쓰였는지로 판정한다. 근거가 없으면 최신 차수를 쓰고 화면에 "추정"으로 표시한다. 같은 코드의 뜻이 차수마다 다른 경우가 있어(예: 104~108) 판정이 필요하다.
  - 2026-09-17 전체 수집 결과: 상장사 업종코드 534종이 모두 11차 분류표에 있고, 11차에만 있는 코드(109, 603, 10520, 10897, 21100, 21212, 21301, 21309)가 쓰여 **DART는 KSIC 11차 기준**으로 확인. 업종코드 자릿수는 3자리 1,128곳·4자리 314곳·5자리 1,314곳으로 섞여 있다.
- **재무 수집 범위 — 전 계정, 5개 재무제표 모두, 금액 열 모두** (2026-09-17): 호출 1번이 주는 응답을 버리지 않는다. 자본변동표(SCE)는 배당·자사주 등 주주환원 분석의 원천이라 포함하고, 전기·전전기 열은 이후 공시의 당기 값과 비교해 소급 재작성을 찾는 데 쓴다. 차트는 각 기간 자신의 보고서 당기 값을 쓴다. 주요 계정 API(`fnlttMultiAcnt`)는 호출이 훨씬 적지만 XBRL 계정 ID·현금흐름표가 없어 쓰지 않는다.
  - 범위 (2026-09-18 3년 → 5년으로 넓힘): 사업보고서는 최근 5개 사업연도, 분기·반기보고서는 올해를 포함한 5개 사업연도(2026년 기준 FY2021~2025 / FY2022~2026). 재무 API는 2015년 이후 자료를 준다. 범위가 넓어지면 스캔 커서의 시작일(`scannedFrom`)이 새 범위를 덮지 못하므로 공시 목록을 처음부터 다시 훑는다.
  - 수집 흐름: 공시 목록(`list.json`, 최종 보고서만)으로 상장사 정기보고서를 장부에 넣고, 받지 않은 보고서를 최신순으로 연결·별도 각각 받는다. 전체 목록은 85일 구간으로 나눠 훑는다 — 회사를 지정하지 않은 검색은 **달력 3개월** 제한이라 2월이 끼면 90일도 거부된다(오류 100). 스캔 커서는 따로 두고 7일 겹쳐 다시 본다.
  - 공시 이름의 `(YYYY.MM)`과 결산월로 보고서 코드·사업연도를 정한다(사업연도 = 그 회계연도가 끝나는 해, 결산월 4월인 회사의 `사업보고서 (2026.04)` → 2026으로 확인). 결산월 기준 3·6·9·12개월째가 아니면(리츠의 6개월 결산 등) 받지 않고 `unsupported`로 둔다. 12월 결산이 아닌 회사의 분기·반기 사업연도 규칙은 실제 응답으로 확인하지 못했다 — 틀리면 아래 확인에서 걸러진다.
  - 응답의 `corp_code`·`bsns_year`·`reprt_code`가 요청과 다르면 저장하지 않는다. 첨부추가처럼 재무제표가 안 바뀐 정정이면 재무 API는 이전 접수번호를 주므로, 그 접수번호로 저장하고 이름에서 `[첨부추가]` 같은 표시를 뗀다.
  - DART는 XBRL 재무가 없는 회사(리츠 등)에 200과 빈 본문을 주기도 한다. 공시당 3회까지 재시도한다.
  - 호출 예산: DART 일일 20,000건 중 재무 수집은 18,000건까지 쓰고(나머지는 기업마스터 몫) 다음 날 00:10 KST에 이어받는다. 3년 범위(보고서 11종)일 때 2026-09-17 실제 스캔 결과 대상 정기보고서 27,877건. 5년 범위(19종)는 같은 비율로 약 48,000건(× 연결·별도 = 최대 약 96,000회) → 약 5~6일로 추정하며, 전체 스캔 후 실제 건수로 고친다. 실측 처리 속도는 초당 약 2회라 하루 18,000건에 약 2.5시간. 기업 하나만 받기는 약 21회(삼성전자 11개 보고서). 재무제표 한 벌은 약 220~230행(삼성전자 연결 기준, 그중 SCE 105행).
- **공공데이터포털 서비스키**: DART 키와 같은 방식 — `passwords.yaml` `shared:`의 `dataGoKrServiceKey` → 환경변수 `DATA_GO_KR_SERVICE_KEY`. 일일 호출은 9,000건까지 쓴다(개발계정 서비스당 10,000건).
- **매일 자동 수집** (2026-09-19): 서버가 켜질 때 반복 예약이 없으면 건다 — 시세 매일 18:00 KST, 재무 매일 18:30 KST(전날 시세가 오후에 올라오므로 저녁). 같은 종류의 수집이 돌고 있으면 건너뛴다. 서버가 꺼져 있는 동안 지난 예약은 다시 켜질 때 한 번 실행되므로 예약을 지우고 다시 걸지 않는다. 로컬 서버라 Mac이 켜져 있어야 한다.
- **수집 중단·재시작** (2026-09-19): 수집은 서버 프로세스 안에서만 돈다. 갑자기 꺼지면 Serverpod가 끊긴 FutureCall을 다음 시작 때 다시 실행하고, 수집은 실행 직전에 작업을 가져와(`IngestJobs.claim`) 실행 중으로 되돌린다(취소된 작업은 돌지 않음). 정상 종료로 실행 예약이 지워졌으면 시작할 때 작업을 "중단됨"으로 정리하고 재무·시세는 이어받기를 예약한다. 판정은 그 작업 번호(`jobId`)를 가진 실행 예약이 남아 있는지로 한다. FutureCall 동시 실행은 4개(기본 1개면 긴 재무 수집 동안 다른 수집이 기다린다).
- **기업 하나 재무 받기**는 전체 수집과 다른 종류(`financial_facts_company`)로 세어 백필 중에도 돈다. 같은 보고서를 동시에 저장하려 하면 늦은 쪽은 "이미 저장됨"으로 처리한다(유일 인덱스).
- **기업마스터는 수동** (2026-09-19): 호출을 아끼려고 매일 자동 수집하지 않는다. 같은 날 재무 수집이 DART 한도를 많이 썼으면 남은 만큼만 받고 "실패"로 멈춘다(전체 갱신이 끝나지 않았으므로 완료로 치지 않음).
- **공공데이터포털 주소는 V2**: 2026년 활용신청은 `GetStockSecuritiesInfoService_V2/getStockPriceInfo_V2`, `GetKrxListedInfoService_V2/getItemInfo_V2`이다. V2가 없는 옛 주소는 오류 12(서비스 없음)를 준다. 키·주소 오류는 `resultType=json`이어도 `OpenAPI_ServiceResponse` 형식(JSON 또는 XML)으로 온다.
- **종목 → 기업 연결 근거는 세 가지, 차례로**(`Security.linkBasis`): ① 상장종목정보의 법인등록번호 = DART 법인등록번호, ② 종목 단축코드 = DART 기업개황의 종목코드(법인등록번호가 `0000000000000`인 외국 기업 등), ③ ISIN 발행체 코드(`KR7` 뒤 5자리)가 이미 ①·②로 연결된 종목과 같음. 상장종목정보에는 우선주가 없어서다 — 2026-09-16 시세 2,871종목 중 115종목이 없고, 그중 114종목이 ③으로 연결되며 한 발행체 코드가 여러 기업에 걸리는 경우는 없었다. 걸리면 잇지 않는다.
- **시세 수집**: 받지 않은 평일 기준일을 최신순으로(처음 5년). 2026-09-18 첫 수집 실측: 평일 1,304일 중 거래일 1,221일 저장, 호출 3,749회·실패 0, 약 25분. 상장사 2,756곳이 모두 종목과 연결됨(연결 안 된 종목 0개). 하루치 약 2,870종목, 페이지당 1,000행. 휴장일도 기록해 다시 조회하지 않되, 게시 전일 수 있는 최근 3일 안의 빈 날은 다시 본다. 이미 받은 (종목, 기준일)은 덮어쓰지 않는다. 등락률처럼 원천 값으로 계산되는 값은 저장하지 않는다.
- **금액 타입**: 원 단위 금액은 BigInt. Serverpod의 BigInt는 DB에 text 컬럼으로 저장되므로 SQL로 합산·정렬하려면 `::numeric` 변환이 필요하다. 업종별 시가총액은 기준일 하루치(약 2,800행)라 서버 Dart에서 합산한다.
- **파생 지표는 화면에서 계산**: PER·PBR·영업이익률·ROE·부채비율과 4분기(= 사업보고서 − 3분기 누적)는 저장하지 않고, 화면에 계산식과 입력 원천 값·접수번호를 함께 보여준다. 최근 12개월 = 전년 사업보고서 + 올해 누적 − 전년 같은 기간 누적. 순이익·자본은 연결이면 지배주주 몫, 별도면 회사 전체. 핵심 계정은 XBRL 계정 ID로만 고르고 이름으로 추측하지 않는다(표준계정을 안 쓰는 금융업 등은 비어 보일 수 있음).
- **화면 구조 — 시장 · 기업 · 데이터** (2026-09-19): 한 페이지에 쌓여 있던 기능을 맨 위 메뉴 셋으로 나눴다. 트레이딩뷰(시장 화면과 종목 화면 분리, 종목 = 헤더 + 탭, Overview는 각 탭의 요약)와 버틀러(기업 화면을 펀더멘탈·밸류에이션·재무·주주환원 등 질문별로 묶음)를 참고했다.
  - 시장(`/market`): 시장별 상장사 수 · 업종별 시총 트리맵 · 업종 분포. 탐색의 시작점이라 트리맵에서 기업 상세로, 업종 분포에서 그 업종의 기업 목록으로 간다.
  - 기업(`/companies`): 검색 · 시장 · 업종(대·중분류) · 정렬 + 목록. 필터는 주소 검색어로 남겨 뒤로가기·링크로 되살린다(필터를 바꿀 때마다 방문 기록을 쌓지는 않음).
  - 기업 상세(`/company/:corpCode`): 오른쪽 패널(440px)에서 전체 페이지로 옮겼다. 헤더에 핵심 지표 6개(시가총액·PER·PBR·영업이익률·ROE·부채비율)를 두고 누르면 재무 탭에서 계산식을 연다. 탭은 개요(각 탭의 요약)와 재무. **빈 탭은 만들지 않는다** — 지배구조 탭은 3단계에서 데이터가 생길 때 더한다.
  - 데이터(`/data`): 원천별 수집 상태와 버튼, 설명. 수집은 예약·이어받기로 서버가 스스로 시작하기도 하므로, 앱 전체에서 한 곳(`IngestMonitor`)이 작업을 지켜보고 끝나면 모든 화면을 새로 고친다. 수집 중이면 "데이터" 메뉴에 점이 깜빡인다.
- **Flutter는 항상 최신 stable** (2026-09-19): 패키지가 SDK와 맞지 않으면 패키지를 낮추지 않고 SDK를 올린다. CI도 버전을 고정하지 않고 최신 stable을 쓴다. Serverpod 생성 코드는 새 SDK 포맷터와 다를 수 있어 CI 포맷 검사에서 뺀다(생성 코드는 고치지 않는다).
- **인증**: 1인 로컬 사용 동안은 없음. 외부 배포 시 Serverpod 기본 인증(이메일)을 켠다.

## 9. 열린 결정

- 상장폐지 기업 포함 여부: 기본은 현재 상장사만, 과거 이력은 3단계 이후.
- 12월 결산이 아닌 회사의 분기·반기 `bsns_year` 규칙 확인 (현재는 판정이 틀리면 응답 확인에서 걸러 실패로 남김).
- 수집한 재무 원천의 실제 저장 크기 측정 (전체 백필 후).
